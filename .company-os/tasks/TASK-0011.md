## Summary

PostgreSQL에서 `platform-workspaces.test.ts > … (REVIEW-0002 R4)`가 가끔 `Error: Hook timed out in 10000ms`(beforeEach, `:53`, 약 10006ms)로 실패했다. REL-0001은 teardown(`db.close()` → `pool.end()`)에서 멈춘다고 적었지만, 실제로 멈춘 곳은 **setup**(`migratePlatform`)이고 원인은 **DB 전체에 걸친 advisory lock 키**다.

## Root Cause

- `packages/core/src/index-store/driver.ts:194`(수정 전): `SELECT pg_advisory_xact_lock(hashtext($1))`에 `tacet:${lock}`만 넣었다. PostgreSQL advisory lock은 schema가 아니라 **DB 전체**에서 공유되므로, 키에 schema가 없으면 같은 DB의 모든 schema가 같은 잠금을 쓴다.
- 이 잠금을 쓰는 곳: `migratePlatform`(`platform/migrations.ts:122`, `"platform-migrations"`), `openIndexDatabase`(`index-store/index-store.ts:146`, `"schema"`), 프로젝트 쓰기(`index-store.ts` `write`, 프로젝트 이름), 워크스페이스 잠금(`workspace:<id>`).
- 테스트는 테스트마다 새 schema를 만들고 `beforeEach`에서 `migratePlatform`을 돌린다. 여러 테스트 파일(전체 `npm test`의 PG 파일 7개)이나 다른 실행이 같은 DB를 쓰면, 서로 상관없는 schema의 마이그레이션이 **하나의 전역 큐**에 줄을 선다. `pg_advisory_xact_lock`은 기다리는 시간에 제한이 없으므로, 앞선 마이그레이션들의 합이 10초를 넘으면 hook이 시간 초과된다.

## Evidence

- 시간: R4 본문은 평소 약 240ms(setup 포함)다. teardown에서 멈췄다면 실패 시간이 10000ms + 본문 ≥ 10200ms였을 것이다. 10006ms는 본문이 실행되지 않았다는 뜻, 즉 **beforeEach setup**(`openSqlDriver` + `migratePlatform`)이 멈췄다(vitest는 setup 정리 함수도 `:53`으로 보고한다).
- 원래 실패 로그(이전 에이전트 `pg-run.log`)는 단일 파일 루프가 아니라 여러 테스트 파일을 함께 돌린 실행이었다. 단일 파일 루프는 수정 전에도 40/40, 4개 병렬 60/60 통과(이전 에이전트의 약 1,000회 중 실패 2회는 모두 병렬 부하에서).
- 계측(pg `Client.query` 래핑): 전체 PG 실행에서 `SELECT pg_advisory_xact_lock(hashtext($1))`가 **다른 파일·다른 schema**(server-accounts, server-workspaces-qa, platform-migrations) 때문에 1.5–2.6초 대기. `pg_stat_activity` 샘플에서도 대기자 3개가 동시에 2.2초씩 기다렸다.
- 재현: 다른 schema에서 느린 마이그레이션(`pg_sleep(12)`)이 잠금을 잡은 채로 workspaces 테스트 파일을 돌리면, 수정 전에는 PG 테스트 2개가 정확히 같은 증상(`Hook timed out in 10000ms`, `:53`, 10003ms/10001ms)으로 실패했다. 수정 후에는 같은 조건에서 39/39 통과.
- 버려진 가설(확인함): 트랜잭션 안에서 pool 사용(코드 전수 확인, 없음), 중단된 트랜잭션 안의 재시도(재시도는 ROLLBACK·release 뒤 새 트랜잭션), 중첩 `transaction()`(호출 없음), PG deadlock(PG 로그에 `deadlock detected` 0건), 풀 고갈(풀 10개보다 큰 16개 동시 가입·생성 스트레스 30회 무정지), pg-pool `end()`의 client 미반납(`end()` 대기 0건).

## Fix

- `driver.ts`: 키에 schema를 넣고 64비트 해시로 바꿨다: `pg_advisory_xact_lock(hashtextextended('tacet:<schema>:<lock>', 0))`. 같은 schema 안의 직렬화(마이그레이션, 프로젝트 쓰기, 워크스페이스 잠금)는 그대로이고, 다른 schema는 서로 기다리지 않는다. 프로젝트 이름이 내부 잠금 이름(`schema`, `platform-migrations`)과 같은 경우의 충돌 범위도 schema 안으로 줄었다. `SqlDriver.transaction` 주석과 ARCHITECTURE.md를 맞췄다.
- 타임아웃은 늘리지 않았다.
- 배포 주의: 잠금 키가 바뀌므로 수정 전 버전과 수정 후 버전 프로세스는 서로를 막지 않는다. 같은 schema에 이전 버전 CLI(`tacet index`, `tacet platform migrate`)를 동시에 돌리지 않는다(Render는 인스턴스 1개).

## Tests

- 회귀: `platform-migrations.test.ts` › "does not wait for migrations in another schema of the database (TASK-0011)" (PG 전용). 다른 schema에서 2초짜리 마이그레이션이 잠금을 잡은 동안 이 schema의 마이그레이션이 먼저 끝나야 한다. 수정 전 키로 되돌리면 `expected 'other schema' to be 'this schema'`로 실패하는 것을 확인했다.
- 스트레스(이전 에이전트가 남긴 것을 유지): `platform-workspaces.test.ts` › "finishes a burst of sign-ups and creates larger than the PostgreSQL pool (TASK-0011)". 풀(10)보다 많은 16개 동시 가입·생성. 트랜잭션 안에서 pool을 쓰거나 실패한 트랜잭션 안에서 재시도하는 회귀가 생기면 멈추거나 실패한다. 남은 주입 버그 없음(`git diff`: src는 `driver.ts`만 변경).
- 결과: PG 루프(`platform-workspaces.test.ts`) 40/40 통과. `npm run build` 통과. `npm test` 272 passed / 1 skipped. PG `npm test` 347 passed / 1 skipped(20 files).

## Production Impact

- 동시 가입·생성은 영향 없음: 가입 트랜잭션은 advisory lock을 쓰지 않고, 풀보다 큰 동시 가입도 멈추지 않는다. 계정 켜기(REL-0001 2단계)를 막던 "동시 가입 시 멈춤"은 코드 결함이 아니었다.
- 같은 PostgreSQL DB를 여러 schema가 함께 쓰면(예: Supabase 프로젝트 하나에 prod/staging schema, 미리보기 배포, 같은 DB에 인덱싱하는 CLI) 수정 전에는 서로의 시작 마이그레이션, 인덱스 schema 생성, 같은 이름 프로젝트 쓰기를 기다렸다. 느린 쪽이 있으면 시작이 제한 없이 늦어질 수 있었다. 이 수정으로 없어진다.
